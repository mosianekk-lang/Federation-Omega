# EvidenceOps Full Maturity Program — 8 August 2026

## Objective
Move the EvidenceOps portfolio from a mixed state of concept/source/local-test/provider-pending capabilities to a governed portfolio where every innovation has an explicit maturity level, current proof, next executable gate, rollback path and retirement rule.

## Core doctrine
Full maturity is not feature count. It is demonstrated correctness, safety, provider truth, recoverability, usability, economic viability and repeatability under real workflows.

## Portfolio maturity gates
Use `evidenceops/maturity/full_maturity_model.json` as the mandatory promotion contract. No capability may claim a maturity level higher than its strongest current evidence.

## Immediate P0 tranche
1. Close repository/provider admission gaps: main protection, Airlock provider readback and direct-push prevention.
2. Close credential and provider-native proof gaps: exposed-key revocation/readback, Secret Manager references, runtime identity binding and bounded canaries.
3. Restore trusted infrastructure path: GitHub-to-Google WIF, inventory readback, deployment authority and immutable receipts.
4. Complete legacy workflow governance: remove unsafe writers, retire duplicate schedules, pin actions and reach strict-mode zero findings.
5. Establish provider-independent EvidenceOps runtime replication and real-workflow calibration for the Algorithm Foundry.

## P1 tranche

2. Mature Alpha-to-Omega deployment adapters with health, drift, persistence and rollback checks.
3. Mature the EvidenceOps Virtual Organization from control-plane source into saleable, bounded fulfilment workflows.
4. Mature eCertify ZA from launch-now boundaries into full-assurance provider, legal, privacy, identity and operational evidence.

## P2 portfolio hardening
- Unified capability registry across innovations, products, agents and algorithms.
- Evidence-linked maturity receipts with source head, provider state, test suite, canary, rollback and review date.
- Automated drift downgrades: maturity decreases when required evidence expires or target state drifts.
- Dependency graph with blast-radius analysis and critical-path ordering.
- Red-team and adversarial evaluation packs per capability class.
- Privacy, retention, data-minimisation and case-wall certification.
- Human-in-the-loop boundaries for consequential legal, financial, identity and publication actions.
- Cost/performance budgets and operational SLOs.
- Commercial readiness: tenant isolation, licensing boundary, supportability, onboarding, telemetry, documentation, demo environment and disaster recovery.

## Exit criteria
The programme is complete only when every in-scope capability is one of:
- `M8 PRODUCTION_MATURE` with current evidence;
- `RETIRED` with migration/retirement proof; or
- `BLOCKED_EXTERNAL` with an exact dependency, safe fallback and no false runtime/production claim.

## Current truth boundary
The repository contains substantial mature source and local/tested controls, but open provider/security/infrastructure issues prevent a truthful portfolio-wide `PRODUCTION_MATURE` declaration. The programme must reduce these blockers before adding lower-value novelty.

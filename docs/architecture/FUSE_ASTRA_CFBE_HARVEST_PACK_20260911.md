## 2. Verified Astra capability primitives harvested

1. Model ID and route: `gpt-6-astra` via Responses API for tool-rich work.
2. Reasoning efforts: `low`, `medium`, `high`, `xhigh`, `max`.
3. Context/output: 1,050,000 token context window; 128,000 max output tokens.
4. Async tool calling: tool can be marked async and result returned by original `call_id`; application still executes and manages pending work.
5. Mid-turn steering: WebSocket continuation can accept user corrections/requirements while preserving completed work.
6. Reasoning update: `configuration_update` input item can change effort mid-conversation while preserving cache.
7. Tools: web search, file search, image generation, code interpreter, hosted shell, apply patch, Skills, computer use, MCP and tool search.
8. Professional work: strong documents, spreadsheets, presentations and template adherence.
9. Computer use: stronger real-software/browser task execution; high-value for Windows/computer-use execution planes when properly connected.
10. Safety/monitoring: stronger boundary adherence but still requires independent FUSE/ProofOS/FDOF controls.

## 5. Integration evolution

The initial recommendation was an additive AIR v2. The deeper harvest supersedes a narrow OpenAI-only implementation by adding `federation/omnisurface_fabric_v2.py`, which keeps Astra as one processor inside a general capability fabric that also covers Luna, Gemini, Copilot, Google Cloud, Apps Script, Canva, Adobe, GitHub, Workspace, Outlook, Windows and bounded capital-intelligence surfaces.

The OmniSurface layer does not execute providers itself. It selects capability routes, validates future-provider attestations, correlates asynchronous calls to FDOF leases, preserves steering continuity and emits deterministic manifests for proof/admission.

## Adaptive 2× cycle

`AdaptiveCycleEngine` treats 2× as a measured target, not an automatic claim.

1. Establish the current performance baseline.
2. Generate or rebuild a candidate.
3. Record attempted routes and self-tests.
4. Reject invariant failures and regressions.
5. Promote `PROMOTE_2X` only when the measured target is reached.
6. Promote a truthful `PROMOTE_INCREMENTAL` when the candidate is better but below 2×.
7. Restructure and rebuild when no gain is measured.
8. Carry only a deduplicated active capsule and delta record into the next cycle.

This prevents the system from manufacturing 2× claims or refusing useful incremental gains.

## Context and code-load control

The active working set is capped by atom count and character budget. Objective, verified facts, decisions, blockers and next actions can be pinned. Exact and near-identical entries are merged, proof references are preserved, and non-active records are represented by content hashes and archive pointers.

The source material is not deleted. Full history belongs in the external evidence plane and is retrieved on demand. The in-process learning ledger and adaptive delta memory retain bounded windows plus cryptographic checkpoints, preventing repeated cycles from expanding chat or runtime context without limit.

Large, duplicated, high-complexity or frequently changed code is routed to a restructuring plan:

- merge duplicate implementations;
- extract stable module boundaries;
- split by responsibility;
- add characterization tests before rebuilding hot code.

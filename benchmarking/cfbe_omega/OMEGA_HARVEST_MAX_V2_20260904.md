## Decision

Ω-HARVEST MAX v2 is an **extension of the existing CFBE Wave-2 scientific capability compiler**, not a new scheduler, memory root, provider executor, proof plane, authority plane, or competing benchmark system.

The improvement moves the harvesting standard from product/feature discovery to **public-source mechanism archaeology**:

`CENSUS → PROVENANCE → TOPOLOGY → DEPENDENCIES → STRUCTURAL IR → CALL/DATA/STATE FLOW → CONCURRENCY/RECOVERY → PERFORMANCE → EVOLUTION HISTORY → NEGATIVE EVIDENCE → BENCHMARK FAIRNESS → PRIMITIVE EXTRACTION → CLEAN-ROOM GENE → RECEIVER EXPERIMENT/VALUE`

The system may inspect public code and public technical evidence deeply. It may not copy proprietary code, infer trade secrets, inherit vendor authority, or treat a benchmark claim as provider/runtime/value proof.

## New executable harvesting controls

### 1. Delta-first source universe

A source-universe plan requires multiple evidence families rather than repeatedly reading one vendor's documentation. The default census spans official docs, source code, tests, benchmarks, commit history and issues, with standards, release notes, PRs, security advisories, package metadata and research as additional families. Content hashes create a harvest watermark so unchanged sources can be skipped on later cycles.

### 2. Information-gain repository slicing

Large repositories are not read linearly. Candidate files are ranked by symbol relevance, change frequency, benchmark/test evidence, dependency centrality, failure history and size penalty. This is intended to minimize context/tool burden while increasing mechanism depth.

### 3. Structural mechanism fingerprints

The first executable fingerprint implementation uses Python AST structure, call names, async/loop/branch/exception/state patterns and deterministic hashes. The contract is designed to accept richer Tree-sitter/SCIP/CodeQL/LST adapters later without changing harvest semantics.

### 4. Equivalence and superset courts

Harvested mechanisms are compared to current Federation capabilities before new build. Exact/near duplicates route toward reuse. Superset analysis identifies which incumbent requirements are preserved, what is missing and what genuine additional primitives are introduced.

### 5. Evolution mining

Commit/PR history is treated as first-class harvest evidence. The miner identifies performance changes, regressions/reverts, security fixes, architecture/runtime changes, tests/benchmarks and repeatedly changed hotspot paths. This allows the system to learn **why** an architecture changed rather than only inspecting its current form.

### 6. Negative-design harvesting

Failures and rejected approaches produce explicit `DO_NOT_REPEAT` rules with causal mechanism, evidence and preferred recovery pattern. Negative evidence is mandatory for completion of a material H7 harvest.

### 7. Hidden-cost surface

A candidate is charged for paid services, remote calls, accelerators, persistent-state services, build dependencies, operating components and manual steps. This prevents a fast-looking benchmark from hiding operational complexity or owner burden.

### 8. License/IP triage boundary

Explicit license metadata is classified conservatively for harvest routing. Unknown, non-standard, copyleft or proprietary cases do **not** authorize copying. Public specifications may still support clean-room behavioural reimplementation. This classifier is engineering triage, not legal advice.

### 9. Independent-source triangulation

Evidence strength is grouped by independent source family/lineage. Multiple pages from one vendor do not become independent confirmation. Contradictory evidence remains visible and can hold gene formation.

### 10. Benchmark preregistration and contamination court

Same-task comparisons pin dataset, implementation, environment, hardware, cache state, authority, cost context, metrics and failure conditions. Hardware mismatch, cache mismatch, dataset mismatch, version mismatch, shared implementation lineage, fixture leakage and cherry-picked subsets fail comparability instead of producing a misleading winner.

### 11. Sequential/Bayesian evidence

Repeated evidence updates a bounded belief model. The sequential court can continue, reject or admit a candidate for further testing without pretending a single benchmark proves superiority.

### 12. Counterfactual and calibration controls

Matched incumbent/challenger observations produce explicit effect deltas; guardrail regressions block attribution. Confidence outputs can be checked with Brier score and expected calibration error rather than treated as self-validating probabilities.

### 13. Adaptive challenger allocation

A deterministic UCB-style allocator balances exploitation of promising mechanisms with exploration of under-tested candidates. This reduces incumbent lock-in and avoids spending all harvest effort on yesterday's winner.

### 14. Pareto + dominance stability

Quality, reliability and proof are maximize dimensions; latency, cost and owner burden are minimize dimensions. A candidate must survive Pareto comparison and repeated-window dominance checks rather than win on one cherry-picked metric.

### 15. Distribution-shift and evaluation-version gates

Reference/current workload distributions are compared before reusing old benchmark conclusions. Dataset/rubric/oracle/environment versions are hash-pinned so benchmark drift cannot silently manufacture progress.

### 16. 14-stage archaeology completion court

The completion court requires H7 depth, substantial stage coverage, at least three independent source groups, at least four source families, estate diff, negative-evidence search, license/clean-room disposition and a pinned benchmark protocol. H9 additionally requires empirical advantage; H10 requires receiver-local value.
